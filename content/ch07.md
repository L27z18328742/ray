# 一批数据如何到达训练 GPU

> 阅读目标：解释 `ray.get(generate.remote(...))`之后，为什么 worker 里还有一次 `ray.get`。状态：已展开。

## 先把变量名里的陷阱拿掉

driver 中变量叫 `rollout_data_ref`，但在默认路线下，它不是单独一个 ObjectRef，而是 **`list[Box]`**。每个 Box 里面存着一个 DP 分片的 ObjectRef。外层方法结果与内层训练数据是两个层次。

```text
generate.remote(id)
   │ 返回外层 ObjectRef（代表 generate 调用）
   ▼ ray.get
driver 得到 [Box(ref_dp0), Box(ref_dp1), ...]
   │ 作为列表传给每个训练 worker
   ▼
worker 按自己的 dp_rank 选择一个 Box
   ▼ ray.get(box.inner)
CPU 上的训练数据 → 显式搬到训练 GPU
```

图示表达引用传递关系，不声称底层数据零复制或永远不经网络。

## 从 Sample 到训练字段

主链：**generate → _convert_samples_to_train_data → _split_train_data_by_dp → ray.put + Box → worker.process_rollout_data → 搬到 GPU**。

1. [RolloutManager.generate](source:slime/ray/rollout.py#RolloutManager.generate)：完成生成后调用转换函数，再返回 DP 分片结果。
2. [_convert_samples_to_train_data](source:slime/ray/rollout.py#RolloutManager._convert_samples_to_train_data)：把 Sample 转成字典，核心字段包括 `tokens`、`response_lengths`、`rewards`、`loss_masks`、`rollout_ids`；可选还有 rollout log probs、多模态输入等。
3. [_split_train_data_by_dp](source:slime/ray/rollout.py#RolloutManager._split_train_data_by_dp)：使用训练侧提供的 `dp_size`等并行配置，计算分区和 microbatch 调度，再打包各 DP rank 的数据。

这里要区分训练循环中的 `rollout_id`（这一轮编号）与数据中的 `rollout_ids`（用于样本归组和训练步调度的轨迹身份）。在一条轨迹拆出多个训练 sample 的场景里，它们不能按“样本位置”随意改写。

## DP 分片不是按训练 Actor 数量随便平分

例如训练 world size 为 4，只有 TP=2、DP=2、PP=CP=1。四个训练进程只对应两个 DP 分片；同一 DP rank 的 TP 成员需要使用对应的数据，而不是给四个 rank 各发互不相同的 prompt。

更简单的教学例子：四条样本、DP=2、每个 microbatch 一条、关闭均衡时，可能形成 DP0 `[0,2]` 与 DP1 `[1,3]`。这只是该简化条件下的示意；真实 [build_dp_schedule](source:slime/utils/dp_schedule.py#build_dp_schedule)会考虑轨迹归组、global batch、microbatch、动态长度、均衡以及 VPP 对齐，不能把固定切片当实现。

manager 的分片字典里，`tokens`等字段按 partition 选择；`raw_reward`和 `total_lengths`仍保留全量，其中部分字段在训练侧再次处理。因此“分片”也不意味着字典每一项都已经变成局部数据。

## Box 具体做了什么

[Box](source:slime/utils/misc.py#Box)只有一个 `_inner`字段和 `inner`属性，没有网络传输算法。manager 的默认分支可以概括为：

```python
# 源码中的核心表达式；外围按 DP rank 循环
rollout_data_refs.append(Box(ray.put(rollout_data)))
```

如果把 ObjectRef 直接作为远程方法的顶层参数，Ray 会在调用执行前解引用。包装 / 嵌套结构让程序能够把引用交到目标 worker，由它选择需要的分片再取数。**这里列表本身也是嵌套容器；不能声称只有 Box 才能实现延迟解引用。**

**设计理解**：driver 只需要操纵引用清单，不必先把所有数据物化到自己进程再转交。实际吞吐、跨节点复制、共享内存行为仍需 profiling，不能从用了 `ray.put`就推导出零拷贝或性能收益。

## 最后一次 get 在训练进程

4. [RayTrainGroup.async_train](source:slime/ray/actor_group.py#RayTrainGroup.async_train)：把整个引用包装列表传给所有 worker。
5. [process_rollout_data](source:slime/utils/data.py#process_rollout_data)：检查列表长度等于 DP size，执行 `ray.get(rollout_data_ref[dp_rank].inner)`；按 partition 处理长度与局部 reward。
6. [MegatronTrainRayActor._get_rollout_data](source:slime/backends/megatron_utils/actor.py#MegatronTrainRayActor._get_rollout_data)：用 Megatron 提供的 DP rank 调用取数函数，然后显式把 token、mask 等 tensor 移到当前加速器。

因此 worker 的 get 是获取训练数据，driver 前面的 get 是等 manager 的方法返回。这两次等待各自有意义。

## 另一个数据传输分支

`rollout_data_transport`默认是 `object-store`，也支持 `nixl`。本版本会为相关 Actors 启用 tensor transport，并在 `ray.put`时选择 `_tensor_transport="nixl"`。这里涉及额外环境与 Ray 接口要求；本教程没有实测该分支。它与第 9 章的**模型权重同步**是不同的数据流。
