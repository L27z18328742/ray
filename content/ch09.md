# 训练完，推理模型怎么拿到新权重

> 阅读目标：把“训练样本传输”和“模型权重同步”两条数据流分开。状态：已展开。

## 训练模型和推理模型是两份状态

训练 worker 更新了自己的参数，不会自动修改 SGLang 进程里的模型。第一次 rollout 前也需要同步：训练侧可能从恢复 checkpoint 加载了与推理初始 checkpoint 不同的状态。

[train.py](source:train.py#train)在创建模型后先调用一次 `actor_model.update_weights()`，之后每轮训练结束再调用。这是显式维护两份模型状态一致性的编排动作。

## 先选对更新器

[create_weight_updater](source:slime/backends/megatron_utils/update_weight/__init__.py#create_weight_updater)按配置选择实现：

| 条件 | 实现 | 本教程覆盖 |
|---|---|---|
| full + nccl + 非 colocate | `UpdateWeightFromDistributed` | 本章主线 |
| 非 disk、colocate | `UpdateWeightFromTensor` | 识别接口，不深入 IPC 细节 |
| full + disk | `UpdateWeightFromDisk` | 第 10 章解释生命周期连接 |
| delta + disk | `UpdateWeightFromDiskDelta` | 仅解释选择条件与限制 |

表中分支有顺序：delta 与 disk 会先被判断，不能只看 colocate 开关。本教程主线选择普通 full / nccl，在 NVIDIA GPU 环境下追分布式权重广播。

## 从 driver 到更新器

主链：**RayTrainGroup.update_weights → 各训练 Actor.update_weights → 获取可更新 engines 和 Lock → 必要时建立通信组 → updater.update_weights**。

1. [RayTrainGroup.update_weights](source:slime/ray/actor_group.py#RayTrainGroup.update_weights)：普通分支提交每个 worker 的更新方法并等待。不要仅按其简短 docstring 把整个实现说成“全局 rank 0 发全部权重”。
2. [MegatronTrainRayActor.update_weights](source:slime/backends/megatron_utils/actor.py#MegatronTrainRayActor.update_weights)：按需恢复故障引擎，向 manager 询问 engines、锁、GPU 数等信息；必要时重新连接更新通信组。
3. [get_updatable_engines_and_lock](source:slime/ray/rollout.py#RolloutManager.get_updatable_engines_and_lock)：本版本选择第一个 `update_weights=True`的模型服务，冻结模型不在其中；并非同时更新所有模型。
4. [UpdateWeightFromDistributed.connect_rollout_engines](source:slime/backends/megatron_utils/update_weight/update_weight_from_distributed.py#UpdateWeightFromDistributed.connect_rollout_engines)：每个 PP stage 中符合 DP / TP 源 rank 条件的训练进程建立对应更新组。暂时忽略 PP 时，可把它看成一个源训练进程连接多个推理 GPU。

## 两条线：控制消息与张量

```text
训练 worker ── Ray 方法(names, dtypes, shapes, version) ──→ SGLangEngine
     │                                                       │ HTTP 控制请求
     │                                                       ▼
     └──────── 分布式 broadcast(参数张量) ─────────────→ SGLang 接收侧
```

在 [update_weights_from_distributed](source:slime/backends/megatron_utils/update_weight/update_weight_from_distributed.py#update_weights_from_distributed)里，先对引擎提交接收命令，再调用 `dist.broadcast`传实际 tensor，等待 broadcast handles，最后上层 `ray.get(refs)`确认接收方法结束。

这里 Ray 参数主要携带名字、类型、形状、group 名和版本等控制信息。权重张量没有通过第 7 章的 `Box(ray.put(...))`路线走。一个是 manager 到训练侧的样本流，一个是训练侧到推理侧的模型状态流。

为什么先提交接收命令再等待？因为接收端可能需要等待广播发送端参与。如果提交后立刻阻塞等待“接收完成”，而发送还没发生，就可能互等。源码在两边都被启动后才等待完成。

## 更新协议是一组有顺序的动作

[UpdateWeightFromDistributed.update_weights](source:slime/backends/megatron_utils/update_weight/update_weight_from_distributed.py#UpdateWeightFromDistributed.update_weights)的大体顺序是：增加版本 → 暂停生成 → flush cache → barrier → 按块整理与传权重 → 必要的量化后处理 → 恢复生成 → barrier。

转换与 gather 由训练后端处理：训练格式中的分片参数需要转换成推理侧需要的名字与张量布局。不要期待“在 Ray 里广播一下 Python 模型对象”就解决并行布局差异。

**设计理解**：暂停与 cache 处理用于协调权重切换边界；锁用于避免多个源并发操作接收端造成通信顺序冲突。它们不能证明任何异常下都具备事务回滚或完全一致的恢复语义。

## 这个 Lock 不是阻塞式锁

[Lock.acquire](source:slime/ray/utils.py#Lock.acquire)检查一个布尔值，获取成功返回 True，失败返回 False。调用方循环尝试并 `sleep(0.1)`；远程锁 Actor 不在自己的 acquire 方法里一直等。

这样默认同步 Actor 仍能处理后续 release 方法。若 acquire 在锁 Actor 内阻塞，release 又在同一个串行队列后面，就可能永远排不到。源码里的锁也没有 lease 或 owner identity；不要据此推导调用者死亡后的自动解锁。
