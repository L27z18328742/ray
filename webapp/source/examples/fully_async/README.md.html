   1 # Fully-Async Rollout Example
   2 
   3 End-to-end demo of slime's fully-async rollout path. A background asyncio
   4 worker keeps a fixed pool of in-flight generations across rollout boundaries,
   5 so the next training step doesn't wait for the slowest in-flight sample.
   6 The worker itself lives in `slime.rollout.fully_async_rollout`; this
   7 directory is just the launch script + CI test.
   8 
   9 ## Files
  10 
  11 * `run-qwen2.5-0.5B-fully_async.sh` — single-node, 4-GPU, three-rollout demo
  12   with Qwen2.5-0.5B-Instruct on dapo-math-17k. Fast enough to be the CI
  13   smoke test for the fully-async path.
  14 * `run-qwen3.5-9B-fully_async.sh` — single-node, 8-GPU, three-rollout demo
  15   with Qwen3.5-9B on dapo-math-17k.
  16 
  17 The same script doubles as `tests/test_qwen2.5_0.5B_fully_async_short.py` in
  18 CI.
  19 
  20 ## Prerequisites
  21 
  22 ```

  42 ## How To Plug Your Own Generate Into This
  43 
  44 Fully-async uses the standard `python3 train.py` entrypoint. Select the
  45 rollout implementation with:
  46 
  47 ```
  48 --rollout-function-path slime.rollout.fully_async_rollout.generate_rollout_fully_async
  49 ```
  50 
  51 For custom per-sample logic, use slime's standard plug-in points — they
  52 work unchanged under fully-async:
  53 
  54 ```
  55 --custom-generate-function-path your.module.generate     # (args, sample, sampling_params) -> Sample | list[Sample]
  56 --custom-rm-path                your.module.reward      # (args, sample | list[Sample]) -> float | list[float]
  57 ```
  58 
  59 See `examples/coding_agent_rl/` for a non-trivial example that plugs in a
  60 multi-turn agent (Claude Code in a Docker-Proxy sandbox) this way.
  61 
  62 ## Worker Internals (Very Short)
  63 
  64 * First call: create a process-wide `AsyncRolloutWorker` (thread + asyncio
  65   loop). The worker is shared across all subsequent `generate_rollout`
  66   calls so its queue stays warm.
  67 * Loop keeps up to `args.sglang_server_concurrency` tasks in flight using
  68   `generate_and_rm_group`.
  69 * Completed groups land on an output queue; each `generate_rollout` call
  70   drains until it has `rollout_batch_size` groups and returns them sorted
  71   by `sample.index`.
  72 * Groups containing an `ABORTED` sample are pushed back into
  73   `data_buffer.add_samples` instead of being shipped to training.
  74 * Worker is stopped automatically at process exit via `atexit`.
  75 
  76 ## Limitations
  77 
  78 * No evaluation mode (would conflict with the continuous-running model).
  79 * Ordering across rollouts is best-effort — within a rollout, groups are
  80   sorted by index before being handed to training.
  81 * TODO: partial-rollout-style resume for `ABORTED` trajectories is not
  82   yet wired; for now the trajectory is re-queued and starts over.
